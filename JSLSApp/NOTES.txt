To make your unit tests truly useful for a compiler, you should focus on testing your compiler phases in isolation using a technique called Data-Driven Testing.

Instead of writing a separate test method for every single JavaScript snippet, xUnit allows you to feed a list of inputs and expected outputs into a
single test structure using the [Theory] and [InlineData] attributes. This keeps your test suite massive, comprehensive, and incredibly easy to maintain.

1. Test Your Lexer (Tokenizer) First

The lexer is the easiest place to start.
You want to pass a string of JavaScript code and verify that it produces the correct sequence of tokens (type and literal value).
```csharp
using Xunit;
using System.Collections.Generic;

public class LexerTests
{
    [Theory]
    // Test simple variable declarations
    [InlineData("let x = 42;", new[] { "LET", "IDENT(x)", "ASSIGN", "INT(42)", "SEMICOLON" })]
    // Test operators
    [InlineData("a + b", new[] { "IDENT(a)", "PLUS", "IDENT(b)" })]
    // Test invalid syntax (lexer should handle errors gracefully)
    [InlineData("@", new[] { "ILLEGAL" })]
    public void Tokenizer_ShouldReturn_ExpectedTokenTypes(string source, string[] expectedTokens)
    {
        // 1. Arrange & Act
        var lexer = new Lexer(source);
        var actualTokens = new List<string>();
        
        Token token;
        do
        {
            token = lexer.NextToken();
            actualTokens.Add(token.ToTestString()); // e.g., "LET" or "IDENT(x)"
        } while (token.Type != TokenType.EOF);

        // Remove EOF for easier assertions if desired, then assert
        actualTokens.RemoveAt(actualTokens.Count - 1); 
        
        // 2. Assert
        Assert.Equal(expectedTokens, actualTokens);
    }
}
```

# What "Lexical Scope" Actually Means
|
Lexical Scope (or static scope) simply means that scope resolution is determined entirely by where a variable is written in the source code,
not when or how the functions are called at runtime.
|
Your original approach mapped perfectly to the structure of the source code (nested scopes looking up to their parents).
Your new approach achieves the exact same lexical resolution, but flattens the runtime memory footprint into a single active lookup dictionary.
|
# Refactoring to a Single Dictionary + Undo Stack
|
Your idea to use a stack to push overwritten nodes when entering a scope, and restoring them when exiting, is an excellent optimization technique.
It gives you O(1) constant time lookups for any variable name, regardless of how deep the scope nesting is.
|
Here is how you can cleanly implement this in C#:
```csharp
public class ScopeManager
{
    // The single, active lookup table for the current position in the AST
    public Dictionary<string, SyntaxNode> LexicalScope { get; } = new();

    // The Undo Stack. It tracks what needs to be restored when a scope exits.
    // We store a list of actions (or previous states) for each scope level.
    private readonly Stack<List<ScopeUndoEntry>> _undoStack = new();

    private struct ScopeUndoEntry
    {
        public string Name;
        public bool ExistedBefore;
        public SyntaxNode PreviousNode; // Null if ExistedBefore is false
    }

    public void EnterScope()
    {
        // Push a new bucket to track changes for this specific scope level
        _undoStack.Push(new List<ScopeUndoEntry>());
    }

    public void DeclareVariable(string name, SyntaxNode node)
    {
        // 1. Record the current state before we overwrite/shadow anything
        var entry = new ScopeUndoEntry { Name = name };
        
        if (LexicalScope.TryGetValue(name, out var oldNode))
        {
            entry.ExistedBefore = true;
            entry.PreviousNode = oldNode; // Capture the shadowed node
        }
        else
        {
            entry.ExistedBefore = false;
        }

        // Log this change to the current scope's undo list
        if (_undoStack.Count > 0)
        {
            _undoStack.Peek().Add(entry);
        }

        // 2. Perform the actual declaration/shadowing
        LexicalScope[name] = node;
    }

    public void ExitScope()
    {
        if (_undoStack.Count == 0) return;

        // Pop the undo log for the scope we are leaving
        var undoList = _undoStack.Pop();

        // Roll back the changes in reverse order
        for (int i = undoList.Count - 1; i >= 0; i--)
        {
            var entry = undoList[i];
            if (entry.ExistedBefore)
            {
                // Restore the shadowed variable from the parent scope
                LexicalScope[entry.Name] = entry.PreviousNode;
            }
            else
            {
                // It was a brand new variable local to this scope; remove it entirely
                LexicalScope.Remove(entry.Name);
            }
        }
    }
}
```

# Direct Comparison: Environment Chain vs. Single Dictionary
|
Feature           | Old Way (Dictionary per Scope)                                                       | New Way (Single Dictionary + Stack)
-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Lookup Speed      | O(N) where N is scope depth (must loop through parent scopes)                        | O(1) constant time (direct hash map lookup)
Memory Allocation | High (allocates a new Dictionary object per block/scope)                             | Low (one persistent Dictionary, tiny struct stack allocations)
Shadowing         | Natural (implicit by stopping at the first match going up)                           | Explicit (handled by pushing to the stack and overwriting)
Persistence       | Good if you need to cache scope state for later analysis (like inside an LSP server) | Destructive (mutates state as you traverse; only reflects the current cursor position)

Is it possible to parse JSON as bytes in JavaScript? The 'data' parameter comes as bytes but I do a very wasteful '.toString()' on it.




<
No, JavaScript’s native JSON.parse() cannot parse raw bytes (ArrayBuffers or Uint8Arrays) directly; it strictly requires a UTF-16 JavaScript string.

However, you can completely avoid the performance hit of a heavy .toString() conversion by using TextDecoder, which decodes bytes directly into JavaScript strings efficiently at the V8 engine level.

The Standard Efficient Way (TextDecoder)

Instead of data.toString(), use a single instance of TextDecoder. It is highly optimized and much faster for streaming data:

```javascript
const decoder = new TextDecoder('utf-8');

languageServer.stdout.on('data', (chunk) => {
  // chunk is a Buffer/Uint8Array
  const jsonString = decoder.decode(chunk, { stream: true });
  
  try {
    const payload = JSON.parse(jsonString);
    // Handle payload
  } catch (e) {
    // Handle partial streaming chunks (see warning below)
  }
});
```

The "Zero-String" Alternative (True Byte Parsing)

If you want to absolutely bypass JavaScript strings entirely for performance, you must use a third-party binary JSON parser written in WebAssembly or highly optimized JS,
such as simdjson_nodejs (which wraps the C++ SIMD-accelerated parser) or json-source-map.

With simdjson, you can pass the native Node.js Buffer directly:
```javascript
const simdjson = require('simdjson');

// Parses directly from the native buffer bytes
const payload = simdjson.parse(chunk); 
```

Critical LSP Warning: Chunk Fragmentation

Because this is an LSP stream, you cannot pass chunk directly to JSON.parse anyway.

TCP/IPC streams fragment data. A single data event might contain:

1. Only half of a JSON payload.
2. The LSP headers (Content-Length: ...\r\n\r\n) mixed with the JSON.
3. Multiple JSON messages stuck together.

You need to maintain a buffer to strip the Content-Length headers and stitch fragmented bytes together before parsing.

LSP messages are split into two parts: an ASCII header (like Content-Length: 123\r\n\r\n) and a raw JSON body. Using reader.ReadLine() will choke on the JSON body because JSON often spans multiple lines, or doesn't end with a newline character at all.

The High-Performance Byte Approach

Instead of StreamReader, you should use Console.OpenStandardInput() directly. You parse the Content-Length header as bytes, and then read exactly that many bytes into a buffer for the JSON payload.

using System;
using System.IO;
using System.Text;
using System.Text.Json;

private static void Main(string[] args)
{
    // 1. Open the raw, un-buffered byte stream
    using Stream stdin = Console.OpenStandardInput();
    
    while (true)
    {
        // 2. Read the headers byte-by-byte until we find the \r\n\r\n delimiter
        int contentLength = ReadHeadersAndGetContentLength(stdin);
        if (contentLength == -1) break; // Stream closed

        // 3. Allocate/Rent a byte buffer strictly for this message's body
        byte[] buffer = new byte[contentLength];
        int bytesRead = 0;
        
        // 4. Force read exactly 'contentLength' bytes
        while (bytesRead < contentLength)
        {
            int read = stdin.Read(buffer, bytesRead, contentLength - bytesRead);
            if (read == 0) break; // End of stream
            bytesRead += read;
        }

        // 5. Zero-string parsing! Pass the ReadOnlySpan<byte> directly to System.Text.Json
        MAIN_decodeMessage(buffer);
    }
}

private static int ReadHeadersAndGetContentLength(Stream stream)
{
    int contentLength = 0;
    StringBuilder headerLine = new StringBuilder();

    while (true)
    {
        int b = stream.ReadByte();
        if (b == -1) return -1; // End of stream

        char c = (char)b;
        if (c == '\n')

            string line = headerLine.ToString().Trim();
            headerLine.Clear();

            }
        }

        {
            headerLine.Append(c);
        }
    }

    return contentLength;
}

does the above code work with respect to "waiting for a message" it won't like eat the CPU while it waits?




<
No, it will not eat your CPU. It will block safely and sleep while waiting for data.

stream.ReadByte() and stdin.Read() are synchronous blocking calls. Under the hood, the operating system puts your application's thread to sleep (into a "Waiting" state) until the Electron app actually writes bytes into the stdin pipe. While the thread is asleep, it consumes 0% CPU.

Why the while(true) is safe here

Even though there is an infinite loop, the loop cannot spin freely. It hits stream.ReadByte(), freezes instantly, and yields all CPU time back to the OS. It only wakes up for a fraction of a millisecond when data arrives, processes it, and immediately freezes again at the next read call.

One small thing to consider

The only time this loop would spin and max out your CPU is if the input stream gets closed or hits an error, and the code fails to exit.

The code provided handles this safely:

```csharp
int b = stream.ReadByte();
if (b == -1) return -1; // StandardInput was closed, breaks the loop safely
```

If Electron closes the app or crashes, ReadByte() returns -1, your method returns -1, and the Main method hits break;, safely shutting down your server without spinning. You are perfectly safe to use this pattern.
