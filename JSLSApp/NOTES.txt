To make your unit tests truly useful for a compiler, you should focus on testing your compiler phases in isolation using a technique called Data-Driven Testing.

Instead of writing a separate test method for every single JavaScript snippet, xUnit allows you to feed a list of inputs and expected outputs into a
single test structure using the [Theory] and [InlineData] attributes. This keeps your test suite massive, comprehensive, and incredibly easy to maintain.

1. Test Your Lexer (Tokenizer) First

The lexer is the easiest place to start.
You want to pass a string of JavaScript code and verify that it produces the correct sequence of tokens (type and literal value).
```csharp
using Xunit;
using System.Collections.Generic;

public class LexerTests
{
    [Theory]
    // Test simple variable declarations
    [InlineData("let x = 42;", new[] { "LET", "IDENT(x)", "ASSIGN", "INT(42)", "SEMICOLON" })]
    // Test operators
    [InlineData("a + b", new[] { "IDENT(a)", "PLUS", "IDENT(b)" })]
    // Test invalid syntax (lexer should handle errors gracefully)
    [InlineData("@", new[] { "ILLEGAL" })]
    public void Tokenizer_ShouldReturn_ExpectedTokenTypes(string source, string[] expectedTokens)
    {
        // 1. Arrange & Act
        var lexer = new Lexer(source);
        var actualTokens = new List<string>();
        
        Token token;
        do
        {
            token = lexer.NextToken();
            actualTokens.Add(token.ToTestString()); // e.g., "LET" or "IDENT(x)"
        } while (token.Type != TokenType.EOF);

        // Remove EOF for easier assertions if desired, then assert
        actualTokens.RemoveAt(actualTokens.Count - 1); 
        
        // 2. Assert
        Assert.Equal(expectedTokens, actualTokens);
    }
}
```

2. Test Your Parser (AST Generation)

For the parser, you want to verify that a string of code builds the correct Abstract Syntax Tree (AST) structure. A great trick here is to implement a
clean ToString() or a serialization method on your AST nodes so you can compare text rather than asserting deeply nested objects.
```csharp
public class ParserTests
{
    [Theory]
    [InlineData("if (true) { return 1; }", "IfStatement(Condition: true, Body: [ReturnStatement(1)])")]
    [InlineData("1 + 2 * 3", "BinaryExpression(+, 1, BinaryExpression(*, 2, 3))")] // Tests operator precedence!
    public void Parser_ShouldBuild_CorrectAst(string source, string expectedAstString)
    {
        var lexer = new Lexer(source);
        var parser = new Parser(lexer);
        
        var program = parser.ParseProgram();
        
        Assert.False(parser.HasErrors(), $"Parser had errors: {string.Join(", ", parser.Errors)}");
        Assert.Equal(expectedAstString, program.ToDebugString());
    }
}
```

3. Core Golden Rules for Compiler Unit Tests
- Test for Failure, Not Just Success: Don't just test valid JavaScript. Create tests that pass invalid JavaScript (like const x = ;) and
  assert that your parser catches the error and populates an error list rather than throwing a hard crash (NullReferenceException).
- Keep Inputs Tiny: A single unit test input should target one behavior (e.g., just testing precedence of * over +, or just testing a while loop).
  Do not feed an entire 50-line script into a single unit test.
- Isolate Components: Never test your Parser by manually constructing tokens. Let the Lexer feed the Parser inside the test, or mock the Lexer.
  (In compilers, letting a real Lexer feed the Parser in tests is generally accepted because Lexers are deterministic and fast).

However, your original approach (one LexicalScope Dictionary per Scope object) wasn't actually wrong—it is known as an Environment Chain.

# What "Lexical Scope" Actually Means
|
Lexical Scope (or static scope) simply means that scope resolution is determined entirely by where a variable is written in the source code,
not when or how the functions are called at runtime.
|
Your original approach mapped perfectly to the structure of the source code (nested scopes looking up to their parents).
Your new approach achieves the exact same lexical resolution, but flattens the runtime memory footprint into a single active lookup dictionary.
|
# Refactoring to a Single Dictionary + Undo Stack
|
Your idea to use a stack to push overwritten nodes when entering a scope, and restoring them when exiting, is an excellent optimization technique.
It gives you O(1) constant time lookups for any variable name, regardless of how deep the scope nesting is.
|
Here is how you can cleanly implement this in C#:
```csharp
public class ScopeManager
{
    // The single, active lookup table for the current position in the AST
    public Dictionary<string, SyntaxNode> LexicalScope { get; } = new();

    // The Undo Stack. It tracks what needs to be restored when a scope exits.
    // We store a list of actions (or previous states) for each scope level.
    private readonly Stack<List<ScopeUndoEntry>> _undoStack = new();

    private struct ScopeUndoEntry
    {
        public string Name;
        public bool ExistedBefore;
        public SyntaxNode PreviousNode; // Null if ExistedBefore is false
    }

    public void EnterScope()
    {
        // Push a new bucket to track changes for this specific scope level
        _undoStack.Push(new List<ScopeUndoEntry>());
    }

    public void DeclareVariable(string name, SyntaxNode node)
    {
        // 1. Record the current state before we overwrite/shadow anything
        var entry = new ScopeUndoEntry { Name = name };
        
        if (LexicalScope.TryGetValue(name, out var oldNode))
        {
            entry.ExistedBefore = true;
            entry.PreviousNode = oldNode; // Capture the shadowed node
        }
        else
        {
            entry.ExistedBefore = false;
        }

        // Log this change to the current scope's undo list
        if (_undoStack.Count > 0)
        {
            _undoStack.Peek().Add(entry);
        }

        // 2. Perform the actual declaration/shadowing
        LexicalScope[name] = node;
    }

    public void ExitScope()
    {
        if (_undoStack.Count == 0) return;

        // Pop the undo log for the scope we are leaving
        var undoList = _undoStack.Pop();

        // Roll back the changes in reverse order
        for (int i = undoList.Count - 1; i >= 0; i--)
        {
            var entry = undoList[i];
            if (entry.ExistedBefore)
            {
                // Restore the shadowed variable from the parent scope
                LexicalScope[entry.Name] = entry.PreviousNode;
            }
            else
            {
                // It was a brand new variable local to this scope; remove it entirely
                LexicalScope.Remove(entry.Name);
            }
        }
    }
}
```

# Direct Comparison: Environment Chain vs. Single Dictionary
|
Feature           | Old Way (Dictionary per Scope)                                                       | New Way (Single Dictionary + Stack)
-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Lookup Speed      | O(N) where N is scope depth (must loop through parent scopes)                        | O(1) constant time (direct hash map lookup)
Memory Allocation | High (allocates a new Dictionary object per block/scope)                             | Low (one persistent Dictionary, tiny struct stack allocations)
Shadowing         | Natural (implicit by stopping at the first match going up)                           | Explicit (handled by pushing to the stack and overwriting)
Persistence       | Good if you need to cache scope state for later analysis (like inside an LSP server) | Destructive (mutates state as you traverse; only reflects the current cursor position)

A Note for LSP (Language Server Protocol) Use

Since your previous message showed you are working on an LSP client/server implementation, keep this one trade-off in mind:

A single mutating LexicalScope dictionary is perfect for a single-pass linear compilation or execution.
However, an LSP server often needs to answer hover or auto-complete queries at any arbitrary random position in the file.
If you mutate a single dictionary as you walk the tree, the dictionary will only represent the state at the very end of the file once the parser completes
